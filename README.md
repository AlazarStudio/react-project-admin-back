# Бэкенд админки ООО «Маяк»

REST API на Node.js + Express 4 + Prisma 6.19 + **PostgreSQL**.
Сделан на базе шаблона студии; MongoDB заменена на PostgreSQL, добавлены
контент-ресурсы сайта (каталог, блог, направления, настройки, заявки, медиа).

## Требования

- **Node.js >= 20.11** (зафиксировано в `engines` в `package.json`). Проверено
  на 24.x. Отдельное требование: команда `npm run seed:export` — и только она —
  дополнительно требует **Node >= 22.18**, потому что импортирует `.ts`
  исходники сайта напрямую. Установке и запуску на сервере это не нужно.
- **PostgreSQL 17** (локально поднимается через `docker-compose.yml`, порт 5434)

## Установка

Каталог сайта для установки НЕ нужен: данные для наполнения лежат в снимке
`prisma/seed-data.json` внутри этого репозитория.

```bash
# 1. БД
docker compose up -d
docker exec mayak-postgres pg_isready -U mayak -d mayak

# 2. Зависимости (postinstall сам выполнит prisma generate)
npm i

# 3. .env — скопируйте .env.example и заполните
cp .env.example .env

# 4. Миграции
npx prisma migrate deploy      # на сервере
npx prisma migrate dev         # в разработке

# 5. Наполнение данными сайта + администратор
npm run seed

# 6. Запуск
npm run dev
```

### Данные для сида

`npm run seed` читает **только** `prisma/seed-data.json` — снимок каталога,
блога, направлений и контактов. Файл лежит в репозитории и обязан там остаться:
без него сид на сервере не отработает и администратор не создастся.

Пересобирать снимок нужно после правок контента в `src/lib/*.ts` — на машине,
где исходники сайта есть под рукой:

```bash
npm run seed:export                  # ищет сайт на два уровня вверх
npm run seed:export -- /var/www/mayak   # или явный путь
SITE_ROOT=/var/www/mayak npm run seed:export
```

Затем закоммитьте изменившийся `prisma/seed-data.json`.

## Безопасность

- Публичная регистрация закрыта: `POST /api/auth/register` требует `protect, admin`.
  Первый администратор создаётся сидом.
- Ответы на неверный логин и на несуществующего пользователя неразличимы,
  время ответа выровнено — перебор логинов не даёт информации.
- Лимиты частоты на `POST /api/auth/login` и `POST /api/leads` — в памяти процесса.
  На входе считаются **только неудачные** попытки, успешный вход обнуляет серию:
  админка запрашивает токен при каждой перезагрузке вкладки и не должна упираться
  в лимит. На заявках лимит стоит **после** проверки `x-api-key`, чтобы аноним
  без ключа всегда получал 401 и не мог выжигать чужую квоту.
  **При нескольких воркерах лимит считается на каждый отдельно**; на проде нужен
  общий стор или лимит на nginx.
- Числовые параметры запроса разбираются строго (`?page=1e9`, `?limit=abc`,
  `?page=0` → 400): «молча подставить значение по умолчанию» — источник багов.
- Ячейки таблиц в `Article.sections` позиционны: пустая ячейка сохраняется,
  каждая строка выравнивается по числу заголовков (`row.length === headers.length`).
  Принимаются оба формата строки — массив ячеек и склеенная переводами строк.
  Непозиционные списки (абзацы, пункты списков, теги, комплектация) от пустых
  элементов, наоборот, очищаются — см. `toCellArray()` против `toStringArray()`.
  Подробности о блоках — в разделе «Блочная модель статьи».
- Автонумерация `sortOrder` не выходит за границу int32, а ошибки Prisma
  никогда не доходят до клиента в сыром виде — `errorHandler` переводит их
  в осмысленные статусы (409 на дубль, 404 на отсутствие, 400 на переполнение).
- Публично отдаётся только опубликованный контент. `?published=all|false`
  и чтение черновика по slug требуют админского токена.
- Загрузка медиа: только растровые изображения (SVG запрещён), проверка
  содержимого через sharp, принудительная перекодировка в WebP, имя и
  расширение генерирует сервер. `/uploads` отдаётся с `X-Content-Type-Options:
  nosniff`, CSP `sandbox` и `Content-Disposition: attachment` для всего,
  что не картинка.
- `PUT /api/config` доступен только администратору; исходящая синхронизация
  `config.json` ограничена allow-list'ом хостов (защита от SSRF).

## Настройки сайта

`GET /api/settings` отдаёт `{ settings, stats, process }`,
`PUT /api/settings` (admin) обновляет **только переданные** ключи — телефоны,
контакты и счётчики, которых нет в теле запроса, остаются как были.

### Что видно в GET кому

`GET /api/settings` публичный, но объём ответа зависит от того, кто спрашивает:

| Кто | Что получает |
| --- | --- |
| аноним | контакты, счётчики, robots, `stats`, `process` |
| админ с JWT | то же + поля доставки заявок |
| сайт с `x-api-key: SITE_API_KEY` | то же + поля доставки заявок |

Поля доставки — `leadEmail`, `leadTelegramChats`, `leadTelegramChatId` — из
анонимного ответа **исключены**: это персональные данные (адрес, куда падают
заявки, и chat_id сотрудников с подписями «кто это»). Публиковать их нельзя
тем более что `docs/DEPLOY.md` допускает вариант с API на поддомене, где порт
доступен снаружи.

Список публичных полей в `setting.controller.js` — **белый** (`PUBLIC_SETTING_FIELDS`):
новое поле по умолчанию не попадает в анонимный ответ, и очередная
персональная настройка не утечёт по забывчивости. Добавляя поле, которое
действительно нужно сайту без токена, впишите его в этот список явно.

> Сайту получатели нужны на сервере для доставки заявок. Он уже держит
> `ADMIN_SITE_API_KEY` (это `SITE_API_KEY` бэкенда) для `POST /api/leads` —
> тот же заголовок `x-api-key` надо передавать и в `GET /api/settings`.

Контактные поля: `phones` (массив), `telegram`, `max`, `email`, `address`.

Счётчики аналитики и доставка заявок — все необязательные, пустая строка
сохраняется как `null`, пробелы по краям срезаются:

| Поле                 | Правило                                                        |
| -------------------- | -------------------------------------------------------------- |
| `yandexMetrikaId`    | только цифры, до 12 знаков (`98765432`)                          |
| `googleAnalyticsId`  | GA4 вида `G-XXXXXXXXXX`; строчные приводятся к верхнему регистру; `UA-…` не принимается |
| `leadTelegramChats`  | список получателей, см. ниже                                     |
| `leadTelegramChatId` | **устарело**, одиночный получатель                               |
| `leadEmail`          | адрес вида `zayavki@example.com`                                 |
| `robotsIndexing`     | boolean, по умолчанию `true` — см. «robots.txt»                   |
| `robotsDisallow`     | массив путей, см. «robots.txt»                                    |

### Получатели уведомлений о заявке

```json
"leadTelegramChats": [
  { "chatId": "362867621",      "label": "Азамат, личка" },
  { "chatId": "-1001234567890", "label": "Отдел продаж" }
]
```

- `chatId` — **строка**, а не число: у групп id отрицательный и длинный,
  у каналов начинается с `-100`, в `Int` такое не влезает. Формат
  `-?\d{1,32}` либо `@username`;
- `label` — подпись «кто это» для панели, необязательная, до **80** символов;
- порядок сохраняется, дубликаты по `chatId` схлопываются (побеждает первое
  вхождение вместе со своей подписью), не более **20** получателей;
- пустой массив допустим и означает «в Telegram не уведомляем».

> `leadTelegramChatId` **устарел**, но не удалён: он остаётся запасным
> вариантом на время рассинхрона выкатки фронта и бэкенда. Порядок выбора при
> доставке: `leadTelegramChats` (если непуст) → `leadTelegramChatId` →
> переменная окружения. Новый код должен писать только в `leadTelegramChats`.

> **Токена Telegram-бота в базе нет и не будет.** Он живёт в `.env` сайта:
> база уезжает в резервные копии, а токен даёт полный доступ к боту. Ни одно
> из полей выше секретом не является.

### Частые вопросы (FAQ)

`FaqItem`: `question` (до **300** символов), `answer` (до **2000**),
`sortOrder`, `published` и `showOnHome` (оба по умолчанию `true`). Оба текста
обязательны и должны быть непустыми строками; нестроковые типы дают 400.

Два флага видимости различают два места показа:

| `published` | `showOnHome` | Где виден вопрос            |
| ----------- | ------------ | --------------------------- |
| `true`      | `true`       | и на `/faq`, и на главной   |
| `true`      | `false`      | только на `/faq`            |
| `false`     | любое        | нигде — `published` главнее |

`showOnHome` принимает **только настоящий boolean**: строка `"false"` даёт 400.
API по этому полю **не фильтрует** — сайт получает список целиком и отбирает
сам (на главной блок короткий, на `/faq` полный), лишний параметр запроса
только мешал бы кэшированию.

Публичный `GET /api/faq` отдаёт только опубликованные; `?published=all`
и `?published=false` требуют админского токена (анониму 403), чтение снятого
с публикации вопроса по id анониму даёт 404.

В исходниках сайта поля называются коротко (`q`/`a`) — сопоставление в
`question`/`answer` делает `npm run seed:export` при сборке снимка.

> **Сид наполняет таблицу только когда она пуста.** FAQ целиком живёт в панели:
> владелец правит формулировки, снимает с публикации, удаляет и добавляет свои
> вопросы. Досоздание по списку воскрешало бы удалённые, а upsert затирал бы
> правки — поэтому непустую таблицу сид не трогает вовсе. Эталон из снимка
> нужен для первой установки, дальше источник истины — панель.

### robots.txt

- `robotsIndexing` — главный выключатель. По умолчанию `true`. При `false`
  сайт целиком закрывается от поисковиков. Принимается **только настоящий
  boolean**: строка `"false"` даёт 400, потому что в JS она истинна и мягкое
  приведение однажды открыло бы сайт вопреки настройке.
- `robotsDisallow` — дополнительные запрещённые пути владельца
  (`/lp-test`, `/old/`). Каждый начинается с `/`, без пробелов, до **200**
  символов; пустые элементы отбрасываются, дубликаты схлопываются, не более
  **50** путей. Пустой массив допустим. Принимается и массив, и текст из
  textarea — по строке на путь.

> Служебные запреты сайта (`/api/`, `/admin`, `/konfigurator`) в базе **не
> хранятся и через панель не редактируются** — они зашиты в коде сайта, чтобы
> не зависеть от содержимого базы. Изменить их — правка кода, а не данных.

## Фотографии товара

У товара две связанные сущности:

- `image` — **обложка**, строка. Обязательна, её использует весь сайт: карточки
  каталога, JSON-LD, модалка. Имя поля историческое, переименованию не подлежит.
- `images` — **галерея**: все фотографии в порядке показа, **включая обложку**.

```json
"images": [
  { "src": "/renders/products/bytovka-stroit.webp", "alt": "Строительная бытовка 6×2.4" },
  { "src": "/uploads/bytovka-inside.webp", "alt": "" }
]
```

Колонка — `Json` (jsonb), а не отдельная таблица: массив читается и пишется
целиком, по отдельным фотографиям не фильтруем и не джойним, а сид и снимок
остаются простыми. Так же устроен `Article.sections`.

Правила:

- `src` — локальный путь от одного `/`. Внешние адреса (`http://`, `https://`,
  протокол-относительные `//host`) отклоняются с 400: на сайте картинки рисует
  `next/image`, и домен, не прописанный в конфиге, роняет страницу;
- `alt` — описание для screen reader'ов, до **300** символов, пробелы по краям
  срезаются. **Пустая строка допустима**: у декоративного изображения alt и
  должен быть пустым;
- дубликаты по `src` схлопываются — побеждает **первое вхождение целиком,
  вместе со своим alt**, порядок сохраняется;
- не более **24** фотографий (предел считается после схлопывания дублей);
- `image` **обязана входить** в `images[].src`, иначе 400;
- при создании без `images` галерея заполняется обложкой, `alt` берётся из
  названия товара — пустой alt на проде выглядит хуже осмысленного описания;
- `PUT` без `images` галерею не трогает, но сменить `image` на фото,
  которого нет в текущей галерее, не даст;
- ради независимой выкатки фронта элемент-строка тоже принимается и
  трактуется как `{ src, alt: "" }`.

Порядок ключей внутри объекта при чтении задаёт jsonb — сравнивать по ключам,
не по порядку полей. Порядок элементов массива сохраняется точно.

### Медиатека

У `Media` есть своё поле `alt` с теми же ограничениями длины. Оно принимается
при загрузке (поле `alt` в multipart-форме), редактируется через
`PUT /api/media/:id` (обновляются только переданные поля) и возвращается
и в списке, и в одиночном чтении.

## Блочная модель статьи

`Article.sections` — массив блоков. Каждый блок обязан иметь `id` (строка,
уникальная в пределах статьи, служит якорем) и `type`, остальные поля зависят
от типа:

| `type`      | Поля                                                              |
| ----------- | ----------------------------------------------------------------- |
| `heading`   | `text`; `level` — 2 или 3 (опц., по умолчанию 2)                    |
| `text`      | `paragraphs` — массив непустых строк, минимум один                 |
| `list`      | `items` — массив непустых строк, минимум один; `ordered` (boolean, опц.) |
| `table`     | `headers` (минимум один), `rows` (массив массивов), `caption` (опц.) |
| `quote`     | `text`; `author` (опц.)                                            |
| `image`     | `src`, `alt`; `caption` (опц.)                                     |
| `gallery`   | `images` — массив `{ src, alt }`, минимум один                      |
| `video`     | `src`; `poster`, `caption` (опц.)                                  |
| `file`      | `url`, `title`                                                     |
| `accordion` | `items` — массив `{ question, answer }`, минимум один               |

Ячейки таблиц **позиционные**: пустая ячейка внутри строки сохраняется, каждая
строка выравнивается по числу заголовков (`row.length === headers.length`).

**Иерархия заголовков.** `H1` занят главным заголовком страницы, поэтому блок
`heading` допускает только `level: 2` (раздел) и `level: 3` (подзаголовок
внутри раздела). Поле необязательное: если его не передать, оно не сохраняется,
а отсутствие означает уровень 2. Любое другое значение (`1`, `4`, `"2"`, `2.5`,
`null`) — 400. Секции старого формата разворачиваются в заголовок уровня 2.

Неизвестный `type`, пустое обязательное поле или дублирующийся `id` дают 400.
Текст ошибки называет индекс блока и его тип
(`sections[2] (type "image"): "alt" is required…`), чтобы админка могла
показать и перевести его.

**Совместимость.** Старый формат секции (`{ id, title, paragraphs?, bullets?,
table? }`) по-прежнему принимается и разворачивается в последовательность
блоков: `heading` из `title` (ему достаётся исходный `id` — якорь не меняется),
затем `text`, `list`, `table` — только заполненные. Производные блоки получают
`id` вида `<id>-text`, `<id>-list`, `<id>-table`. Смешанный массив тоже
допустим, поэтому фронт и бэкенд выкатываются независимо.

Реализация — `app/article/article-blocks.js`.

> Порядок ключей внутри блока при чтении может отличаться от отправленного:
> это канонизация PostgreSQL `jsonb`. Порядок блоков, строк и ячеек
> (то есть всех массивов) сохраняется точно.

## Эндпоинты

Приватные маршруты требуют заголовок `Authorization: Bearer <JWT>`,
маршруты с пометкой **admin** — роль `SUPERADMIN`.

### Аутентификация и пользователи

| Метод | Путь                  | Доступ  |
| ----- | --------------------- | ------- |
| POST  | `/api/auth/register`  | **admin** (публичной регистрации нет) |
| POST  | `/api/auth/login`     | Public (лимит частоты) |
| GET   | `/api/users/profile`  | Private |
| PUT   | `/api/users/profile`  | Private |

### Контент (GET — публичный, запись — admin)

| Метод              | Путь                          | Доступ |
| ------------------ | ----------------------------- | ------ |
| GET                | `/api/products`               | Public |
| GET                | `/api/products/:idOrSlug`     | Public |
| POST/PUT/DELETE    | `/api/products[/:idOrSlug]`   | admin  |
| GET                | `/api/articles`               | Public |
| GET                | `/api/articles/:idOrSlug`     | Public |
| POST/PUT/DELETE    | `/api/articles[/:idOrSlug]`   | admin  |
| GET                | `/api/solutions`              | Public |
| GET                | `/api/solutions/:idOrKey`     | Public |
| POST/PUT/DELETE    | `/api/solutions[/:idOrKey]`   | admin  |
| GET                | `/api/settings`               | Public |
| PUT                | `/api/settings`               | admin  |
| GET                | `/api/settings/stats`         | Public |
| POST/PUT/DELETE    | `/api/settings/stats[/:id]`   | admin  |
| GET                | `/api/settings/process`       | Public |
| POST/PUT/DELETE    | `/api/settings/process[/:id]` | admin  |
| GET                | `/api/faq`                    | Public |
| GET                | `/api/faq/:id`                | Public |
| POST/PUT/DELETE    | `/api/faq[/:id]`              | admin  |

Списки отдают `{ items, pagination }`. По умолчанию возвращаются только
опубликованные записи. `?published=all` (с черновиками) и `?published=false`
(только черновики) **требуют админского токена** — анониму 403. Чтение
неопубликованной записи по slug анониму отдаёт 404.

Есть `?page`, `?limit`, `?search` и фильтры ресурса. Фильтры принимаются
только строками: `?type[contains]=…` вернёт 400, а не молча весь список.
Спецсимволы `%` и `_` в `?search` экранируются.

### Заявки

| Метод  | Путь              | Доступ                       |
| ------ | ----------------- | ---------------------------- |
| POST   | `/api/leads`      | Public + `x-api-key` + лимит частоты |
| GET    | `/api/leads`      | admin                        |
| GET    | `/api/leads/:id`  | admin                        |
| PUT    | `/api/leads/:id`  | admin                        |
| DELETE | `/api/leads/:id`  | admin                        |

### Медиа (всё — admin)

`POST /api/media/upload`, `/upload-document`, `/upload-video` (поле `file`),
`GET /api/media`, `GET|PUT|DELETE /api/media/:id`.
Префикс `/api/admin/media` сохранён как алиас для совместимости.

Принимаются **только растровые изображения** (jpeg, png, webp, gif, avif,
tiff, bmp) — всё остальное 415, превышение размера 413. Все три маршрута
ведут себя одинаково: `upload-document` и `upload-video` остались алиасами
ради совместимости, документы и видео сейчас не поддерживаются.
Загруженное принудительно перекодируется в WebP.

### Служебное

`GET /api/health` — статус сервера и БД.
`GET /api/config` — публичный, `PUT /api/config` — **admin**.

## Скрипты

- `npm run dev` — nodemon.
- `npm run seed` — наполнение БД из `prisma/seed-data.json`. Каталог сайта не
  требуется. Идемпотентен и не разрушителен: контент обновляется upsert'ом,
  id вложенных записей сохраняются, **учётка администратора не перезаписывается**.
- `npm run seed:export` — пересборка снимка `prisma/seed-data.json` из
  `src/lib/*.ts`. Нужен каталог сайта и Node >= 22.18.
- `npm run prisma` — Prisma CLI. `npx prisma studio` — визуальный редактор БД.
- `postinstall` автоматически выполняет `prisma generate` — после `git clone`
  и `npm i` сервер импортируется без ручных шагов.

## Создание нового ресурса

Возьмите за образец готовый модуль — например `app/faq` (простой) или
`app/product` (со сложной валидацией): контроллер, роуты, модель в
`prisma/schema.prisma`, подключение в `server.js`, затем `npx prisma migrate dev`.

## Известные ограничения

**Генератор ресурсов из шаблона удалён** — вместе с `app/generate`,
`app/utils/code-generator.js`, `app/utils/structure-model-sync.js`,
`scripts/reset-generated.mjs` и заготовкой `app/_empty`. Он написан под MongoDB,
а на PostgreSQL был прямо опасен: `POST /api/admin/generate/resource`
переписывал `prisma/schema.prisma`, правил `server.js` и выполнял
`prisma db push --accept-data-loss` — то есть рассинхронизировал историю
миграций и мог уничтожить данные. Ресурсы здесь добавляются руками, по образцу
готового модуля (см. «Создание нового ресурса»).

**Лимиты частоты живут в памяти процесса.** При запуске в несколько воркеров
лимит применяется к каждому отдельно.
